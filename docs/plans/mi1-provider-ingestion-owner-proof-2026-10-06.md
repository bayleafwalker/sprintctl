## What crosses the boundary

`165bb45c53a097575c6bd497dd352b2697ad190c`. It records that source path and
SHA256, the **synthetic** GitHub input, and four distinct delivery identities.
It is not evidence of a real webhook, signed provider message or live capture.
No copy of that decoder is imported into Sprintctl or installed as a new runtime
dependency. These are an external producer's actual draft fields, checked
against the owner's published append schema.

The tests register a real run on a new disposable PostgreSQL16 authority, resolve
its principal/workspace/client/grant binding, and add the run and observed empty

## Histories and oracles

- Offline capture and duplicate capture have no effective owner evidence.
  Commit-before-reply-loss leaves an uncertain producer attempt. Exact retry
  confirms the first receipt with one owner item and one ledger row.
- Changed artifact under one delivery keeps its key and changes semantic
  content. A second producer receives `idempotency-conflict`, remains pending
  and cannot replace the first owner tail or history.
- A recorded provider success on an artifact different from the proposed
  intent remains an observation with null grant and null confirmation. It
  neither settles the work nor accepts the effect. Its public proposer cannot
  call accept or mark-applied: both return `authority-required`/403, preserving
  work and intent records. This does not assert that an authorized protected
  acceptor is unable to make an independent Decision.
- Two independent owner connections, with the existing deterministic native
  lock barrier, receive the same evidence receipt while one waits on the
  other. Two producer stores confirm; only one evidence item/ledger row exists.

The assertion that stored records survive without the integration reads them
through the native owner alone; the provider decoder is never loaded in these
tests. This proves removal of this observation adapter does not move authority
or erase admitted history. It does not prove a production package rollback.

These are bounded application and concurrency examples, not a universal
linearizability, HTTP authentication, signature-verification or full S4 proof.
All PostgreSQL cases use the repository's guarded disposable runner; never aim
them at a shared database. The runner independently verifies zero-row fixture
cleanup.
