# Vuoro UX Robustness — Repo-Scope Disambiguation and Silent-Failure Elimination

Status: planned (dispatch-plan output, 2026-07-25; opus-authored brief + addendum,
folded in and reconciled against live findings by the orchestrating session)
Related items: none filed yet — filing is deferred; see "Filing status" below.
Related docs: `docs/plans/served-mode-gaps-plan.md` (the investigation that
surfaced this tract), `docs/reference/doc-refs.md` (ref/frontmatter convention
this doc follows)

## Why this is its own tract, not a served-mode-gaps sub-item

While verifying `served-mode-gaps-plan.md`'s item citations (#1247-#1251 at
the time, now #1982-#1986 after recovery — see that doc's renumbering note),
two independent sessions produced conflicting explanations for why the cited
items 404'd: cwd/repo_id confusion vs. "maybe never filed." Chasing that
disagreement to ground truth surfaced a cluster of related-but-distinct
defects in how sprintctl's CLI resolves and reports implicit context (which
repo, which backend, which database), all sharing one root cause: **cwd- and
env-derived implicit context is a systemic hazard in this CLI, and served/
remote mode converts what should be loud failures into confident-looking
wrong answers.** That is broader than any single served-mode-gaps sub-item
and is scoped here as its own tract.

The investigation that produced this brief is fully resolved as fact, not
hypothesis — see "Investigation findings, now resolved" below. The migration
and read-only lockdown it motivated have **already been executed** (2026-07-25,
same session) — see "Already executed" below. What remains is the CLI/doctor/
agent-guidance work itself (D1-D10).

## Investigation findings, now resolved

1. **Bug #1 (repo_id ambiguity, live):** `sprintctl item show --id N` resolves
   `repo_id` purely from `.sprintctl/backend.json` found by walking upward
   from cwd (`backend.py:resolve_repo_identity`, line 89), with no
   `--repo-id` override on read commands. Work-item IDs are `UNIQUE
   (repo_id, id)`, not globally unique, so a bare number run from the wrong
   checkout silently returns a real, different, unrelated item — confirmed by
   reproducing the exact devbox-session symptom (`item show --id 1250` from
   `/projects/dev/agentops` returned a real done agentops item, not an error).

2. **Bug #2 (data-plane divergence), now root-caused, not just observed:**
   `sprintctl-pg` (192.168.20.220, devbox-agent's stale default
   `SPRINTCTL_URL`) is `sprintctl-cnpg-main`, a **legacy, pre-#1195-cutover**
   CloudNativePG cluster in the `vscode` namespace — architecturally separate
   from `vuoro-shared-db`, the database `served` mode actually reads.
   `vuoro-shared-db`'s `networkpolicy-sprintctl-backfill.yaml` documents a
   **one-off**, not continuous, backfill of "each still-direct-remote
   workstation repo's history," run once per repo as each of 7 workstation
   repos cut over. Items #1247-#1251 (now #1982-#1986) were filed via the
   direct-remote CLI path against the legacy DB on 2026-07-24, after
   sprintctl's own backfill window had already closed, so they never synced.
   This is confirmed by direct inspection of both databases, not inferred.

3. **New failure mode found live (Axis 2, independent of bug #1):**
   env-forced backend mode can silently override the repo marker with **no
   warning outside `doctor`, and not even then unless a marker happens to be
   in scope**. From a marker-less cwd, `SPRINTCTL_BACKEND=remote` (devbox-
   agent's stale global default) resolves cleanly with no corroboration and
   returns a confident `Item #N not found.` against the wrong database — this
   is what actually explained the original devbox-session confusion, not bug
   #1's cwd/repo_id issue (which explains a *different* symptom — resolving
   to a real wrong item rather than a false not-found). From inside the
   sprintctl checkout (marker present), the identical misconfiguration IS
   caught (`backend-config-invalid`) — so the enforcement logic is already
   correct, it just isn't applied when there's no marker to trigger it.

4. **Schema fact that shapes the whole reference-scheme design:**
   `work_item.id` is `bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` —
   **one global identity sequence shared across every `repo_id` tenant** in a
   given Postgres instance (`pg.py:112-113`), with `UNIQUE (repo_id, id)` only
   as a secondary constraint. A migrated/recovered row cannot be inserted
   under its original number if that number is already taken by another
   tenant — confirmed in practice during the recovery migration (#1247-#1251
   landed as #1982-#1986, not their original numbers). `aggregate_uuid`
   (`NOT NULL UNIQUE` on `sprint`/`work_item`) is already in the schema as a
   true global stable key, independent of this design's outcome.

5. **Existing precedent already in the codebase:** `migrate-to-remote`
   (`cli.py:8374`) has a `--repo-id` assert flag that fails closed on
   mismatch (`cli.py:8414`), and the evidence-pilot append command
   (`cli.py:2279`) has a softer explicit-`--repo-id`-else-cwd fallback. The
   fix below generalizes these existing patterns rather than inventing a new
   one.

## Goal

Make every sprintctl work-item reference and every backend/repo resolution
self-evident about what it targets on the shared multi-tenant substrate, so
a reference cited in a plan doc, commit, or chat resolves to exactly one
intended item and one intended database — or fails loudly and specifically —
without sacrificing the short, memorable form humans and agents actually use
in conversation (`#1247`-style citation).

## Decisions (a build worker executes without re-deciding)

**D1 — Bug #2 is not this tract's implementation scope.** It was root-caused
and remediated directly (see "Already executed") rather than folded into a
client-side CLI change. This tract's D2-D10 concern *prevention* of a
recurrence and of the broader silent-failure class, not the specific
historical recovery, which is done.

**D2 — Reference scheme: `repo#id` prefixed display, dual-form input parser,
no schema change.** Weighed against a bare integer (fails: no collision
protection — this is what caused the original misdiagnosis), a raw
`aggregate_uuid` (fails: not memorable/typeable in chat), and a
`repo#sprint#id` triple (rejected: sprint_id doesn't add disambiguation
beyond `repo_id`, which is already the schema's actual uniqueness key, and
couples a stable reference to a mutable grouping). `repo#id` (e.g.
`sprintctl#1247`) satisfies both memorability and disambiguation. `--id`
accepts both `1247` (scoped to the resolved repo) and `sprintctl#1247`
(explicit scope, which also feeds D3's precedence and D-new's fail-closed
assert). Presentation/parse layer only — no PK, sequence, or column change
(finding 4 makes this a hard constraint, not a preference: the `Backend
parity` closed subject in `.agents/overlays/sprintctl.state-protocols.md`
is depth-2, an irreversible multi-object schema change would need Depth-3
escalation).

**D3 — repo_id precedence: explicit reference/flag > committed marker >
`SPRINTCTL_REPO_ID` > cwd-derived compatibility fallback.** Explicit-vs-marker
or explicit-vs-cwd mismatch always fails closed, reusing the existing
`migrate-to-remote` assert error shape (`cli.py:8414`). An environment value
cannot silently override a committed marker. Note: this precedence resolves
*which repo* (Axis 1) — it does not by itself catch Axis 2 (finding 3), which
needs D-new below; a marker-less cwd has no repo_id conflict for D3 to detect.

**D4 — Server change is scope-reporting only, not new authorization.**
`application.py`'s existing `Identity.authorizes_repo` already gates access;
a shared devbox credential is legitimately authorized for many repos, so a
server round-trip alone would confirm a wrong-but-authorized query, not
reject it. Instead, every command echoes resolved `repo_id` + its source
(flag/env/cwd) alongside its result, so a not-found or empty result names
what it was produced against.

**D5 — Universal backend-preflight (Axis 2 fix), not just `item show`/
`doctor`.** One shared `backend.py` preflight helper, invoked by every
command regardless of whether a marker happens to be in scope. It:
(a) resolves backend mode + target + source; (b) runs the marker-vs-env
corroboration that already exists (`backend.py:228-233`) but today only
fires when a marker is present; (c) surfaces (a)+(b) uniformly. This also
removes the standing inconsistency where `item list`/`sprint show`/`event
list` skip any check and fail with a raw, undiagnosed connection error
(full served-mode support for those commands remains #1984's separate
scope — this tract only makes their *failure mode* consistent and
diagnosed, not their happy path complete).

**D6 — Loud resolved-context echo on every command (Axis 2 analog of D4).**
Every command's output — success, not-found, or empty — names
`backend=<mode> target=<endpoint, credential-redacted> source=<marker|env|
flag>` alongside D4's repo_id echo. `Item sprintctl#1195 not found
(backend=remote, target=192.168.20.220:5432/sprintctl, source=env).` This
one line would have prevented the original devbox-session misdiagnosis
directly. Redact credentials per the existing `_redacted_postgres_error`
helper (`cli.py:140`).

**D7 — Fail-closed on uncorroborated non-local backend from a marker-less
cwd.** New rule, orthogonal to D3: marker-less `remote` or `served` execution
fails closed unless the invocation supplies both explicit `--repo-id` and an
invocation-scoped opt-in flag. `local` mode is exempt.

There is no persistent environment allowlist; this closes finding 3, which
D3 alone cannot catch from a marker-less cwd.

**D8 — Silent-failure taxonomy is a first-class `doctor` + preflight
contract.** `doctor` and the D5 preflight both check and label each known
class:

| Class | Cause | Doctor | Preflight |
|---|---|---|---|
| SF1 | Axis 1: bare-numeric cross-repo collision | note resolved repo_id + source | D3 assert + D6 echo |
| SF2 | Axis 2: env overrides marker / uncorroborated backend | already `backend-config-invalid` when marker present; add `backend-uncorroborated` when marker absent + non-local env | D7 fail-closed + D6 echo |
| SF3 | Axis 3: legacy-DB / served-read divergence | now resolved by "Already executed," but doctor should still probe and warn if a target looks legacy/superseded (checks for D-new-1's tombstone) | n/a — remediated, not a live code path |
| SF2-b | legacy/empty backend target reachable but unpopulated | doctor warns "backend reachable but holds no current sprint data" | D6 echo makes target visible regardless |

**D-new-1 — Tombstone detection, client side (complements the already-applied
DB-level lockdown).** The `superseded_marker` table added during "Already
executed" is inert today — no command looks for it. Wire the D5 preflight
to check for it when connecting to a `remote` target and, if present, fail
closed with the tombstone's own message (`this database was superseded ...,
see ...`) instead of a bare permission-denied error. This is the client-side
half of finding 2's fix; the server-side half (revoke) is already done.

## Resolved policy and remaining operator questions

- **O1 (resolved, 2026-07-26):** fail closed by default for marker-less
  `remote` or `served` execution. The narrow exception is explicit
  `--repo-id` plus the invocation-scoped opt-in in D7; echo-and-proceed is
  not acceptable.
- **O5 (architecture, devbox-agent env split) — materially de-risked by
  "Already executed," but not fully closed:** `~/.config/actionq-env` on
  devbox-agent is both the interactive-shell default *and* the actionq-
  dispatcher daemon's systemd `EnvironmentFile`
  (`gitops-nixos/modules/system/actionq-dispatch.nix`), whose
  `[global.sprintctl_takeup] remote_only = true` and per-project
  `SPRINTCTL_BACKEND=remote` override its own internal pre-dispatch gates.
  The read-only lockdown means an uncorrected default now fails loudly
  instead of silently — so this is no longer a correctness emergency — but
  the daemon's gates still can't write (they never could meaningfully,
  post-lockdown) and its env still doesn't reflect served-mode reality.
  Decide: split interactive vs. daemon env sources, or reconcile
  `sprintctl_takeup` to speak served mode. This tract's client-side code
  does not depend on this being resolved.
- **O6 (resolved, 2026-07-26):** use explicit `--repo-id` plus an
  invocation-scoped opt-in flag. Do not add `SPRINTCTL_ALLOW_UNCORROBORATED_BACKEND`
  or any other persistent global bypass. Daemon/service environments must
  identify the repository explicitly or provide a marker; reconcile their
  environment split separately before D7 rollout.
- **O9 (new — lockdown durability):** the legacy-DB revoke from "Already
  executed" is git-recorded but not GitOps-enforced (no managed-roles/
  postInitSQL block, applied via direct `kubectl exec`). Worth a follow-up
  to encode it durably against the CNPG cluster, or accept it as a one-time
  operator action with the risk noted? Separate from this tract's CLI scope;
  raise as its own small appservice item once filing is unblocked.
- **O10 (new — devbox-agent read-profile bug):** the independently-found
  "devbox-agent's served read profile 404s on real items while workstation's
  doesn't" needs triage. Not scoped or root-caused here; raise as its own
  item once filing is unblocked, referencing item #1989 where it's logged.

## Scope

**Allowed:** `sprintctl/backend.py` (env var, precedence funnel, preflight
helper, tombstone check), `sprintctl/cli.py` (shared `--repo-id` option,
`repo#id` parsing on ambiguity-prone commands, echo output, self-referencing
command strings), `sprintctl/application.py`/`served.py` (surface existing
`repo_id` in payloads — no new authorization), `sprintctl/doctor.py` (SF1-SF3
diagnostics), docs (`AGENTS.md`, `docs/reference/doc-refs.md`, the
`dispatch-plan`/`task-pickup`/`item-done` skill docs — require `repo#id`
citation, note the shared-substrate hazard), tests.

**Out of scope:** any schema/PK/identity-sequence change or migration
(Backend-parity closed subject; would need Depth-3); new server-side
authorization; full served-mode support for `item list`/`sprint show`/
`event list`/`item add` (remains #1984, this tract only makes their failure
*diagnosed*, not complete); O5/O6/O9/O10 (separate follow-ups once filing is
unblocked).

## Acceptance checks

1. From `/projects/dev/agentops`, `sprintctl item show --id sprintctl#1195`
   errors with a repo-mismatch message instead of any wrong result.
2. From any cwd, `SPRINTCTL_REPO_ID=sprintctl sprintctl item show --id 1195`
   resolves `repo_id=sprintctl` regardless of cwd.
3. Every `item show` output (found and not-found) names resolved `repo_id`
   and its source (D4).
4. From a marker-less cwd with `SPRINTCTL_BACKEND=remote` in env, every
   command (`item show`, `item list`, `sprint show`, `event list`) fails
   closed per D7 (not a silent not-found/empty result) unless the D7/O6
   opt-in is present.
5. Every command echoes resolved `backend`/`target`/`source` (D6);
   not-found and empty-result outputs name the backend they were produced
   against.
6. `item list`/`sprint show`/`event list` run the same D5 preflight as
   `doctor`/`item show` — no command reaches a raw connection error without
   a diagnosed preflight first.
7. `doctor` emits distinct, labeled diagnostics for SF1/SF2/SF2-b per the D8
   table, including `backend-uncorroborated` from a marker-less non-local
   env, and a tombstone-aware warning if a `remote` target carries a
   `superseded_marker` row.
8. `AGENTS.md`/`doc-refs.md` require `repo#id` citation form.
9. Precedence flag > env > cwd holds (D3); explicit-vs-cwd mismatch always
   asserts.
10. No schema/migration diff; local SQLite single-repo workflows unchanged.
11. A `remote` target carrying a `superseded_marker` row fails closed with
    that row's message (D-new-1), verified against a disposable fixture
    database, never against the real legacy DB.
